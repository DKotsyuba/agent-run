# Qwen Code 0.22.2 probe

- Headless output: `qwen -p PROMPT --output-format stream-json --approval-mode MODE`. Output is JSONL: `system/init`, optional `stream_event`, `assistant` (text at `message.content[].text`, usage at `message.usage`), then `result` (final text at `result`, totals at `usage.input_tokens`, `usage.output_tokens`, and cached input at `usage.cache_read_input_tokens`).
- Permissions: `plan` exposes read-only tools and prevents edits; `auto-edit` permits edits. An explicit mode is mandatory for every adapter launch. `yolo` is deliberately not used. Verified live (T080): in headless (`-p`) mode, `plan` denies every tool that would otherwise prompt for confirmation, including plain reads (`read_file`, `grep_search`) -- there is no TUI to fall back to, so a `plan` child can only reason from its own context and prior turns, not the filesystem. `auto-edit` allows file-editing tools (`write_file`, MCP tools once trusted -- see below) but still denies `run_shell_command`; only `yolo` (deliberately unused) would auto-approve shell commands.
- Auth type is a **separate, mandatory setting** from provider env vars: without `security.auth.selectedType: "openai"` in `settings.json`, a headless run fails closed with `"No auth type is selected. Please configure an auth type ... before running in non-interactive mode."` even when `OPENAI_API_KEY`/`OPENAI_BASE_URL`/`OPENAI_MODEL` are all correctly exported (verified live, T080, both against an unreachable loopback endpoint and against the real OmniRoute router). The adapter now always renders this field; T079's probe result above (provider env vars alone suffice) was evidently against a `HOME` with a previously-cached interactive auth selection, not a fresh one -- do not trust that finding for a fresh generated home.
- Provider: `OPENAI_BASE_URL`, `OPENAI_API_KEY`, and `OPENAI_MODEL` selected an arbitrary OpenAI-compatible endpoint and model in `-p` mode without `/auth` (verified against an intentionally unreachable loopback endpoint; init reported the supplied model) -- provided `security.auth.selectedType` is also set, per above.
- Auth fallback (T080): when `OPENAI_API_KEY` is absent from the process environment, the adapter (`adapters/qwen/auth.py`) reads the same managed OmniRoute keychain item the OpenCode server password helper reads, via `/usr/bin/security find-generic-password -a OMNIROUTE_API_KEY -s com.pluto.agent-run.opencode.omniroute -w <real-login-keychain-path>`. The keychain path must be given explicitly and must be the *real* login keychain (`pwd.getpwuid(os.getuid()).pw_dir`, not `$HOME`) -- a sandboxed or generated `$HOME` has no keychain search list of its own and the lookup silently returns "item not found" without the explicit `-w` path. When `OPENAI_BASE_URL` is absent, the adapter defaults it to `http://127.0.0.1:20128/v1` (the local OmniRoute router). The process environment always wins over both fallbacks.
- MCP/context: Qwen settings use `mcpServers` for stdio servers and `context.fileName` for the context contract. The adapter gives the context file a per-run absolute name, so ambient `QWEN.md` is not selected. **MCP trust (T080):** an `mcpServers.<NAME>` entry needs `"trust": true` for a headless run to actually use its tools -- without it, every MCP tool call is silently denied with `"Tool blocked ... requires a permission grant that can't be obtained in this non-interactive mode"` even under `auto-edit`, because there is no prompt to answer. Verified live end to end: a child asked to call `mcp__agent_lsp__list_symbols` on this adapter's own `auth.py` was denied until `trust: true` was added, then it called the tool, got a real result (6 top-level symbols, matching the file), and reported it.
- Skills (T080): Qwen has no Skill tool. The adapter (`adapters/qwen/skills.py`) delivers configured `config.skills` by copying each one's `SKILL.md` to `<home>/skills/<name>/SKILL.md` (plugin-owned names resolved the same way codex/opencode resolve them, via `agent_run.adapters.plugin_skills.skill_dirs`) and appends a paragraph to the injected context file naming the absolute `<home>/skills` path and the configured skill names, so the model can `read_file` each `SKILL.md` itself.
- Hooks (T080 -- supersedes the T079 TODO below): the bundled docs at `node_modules/@qwen-code/qwen-code/bundled/qc-helper/docs/features/hooks.md` fully document the settings schema (`hooks.<Event>: [{matcher, hooks: [{type: "command", command, ...}]}]`), and it **works live with no extra trust step**, unlike codex's `[hooks.state]` digest requirement. Verified: a `PreToolUse` command hook configured this way fired on a `read_file` tool call in a throwaway `HOME` and received the documented JSON payload (`tool_name`, `tool_input`, `session_id`, ...) on stdin. The adapter now renders `config.hooks` into `settings.json`'s `hooks` table (`adapters/qwen/adapter.py:_hooks_document`), expanding `{plugin:NAME}` command tokens against plugin copies installed by `adapters/qwen/plugins.py` (a qwen-specific, much simpler analog of `adapters/codex/plugins.py` -- no marketplace, no manifest, no trust digest, just a verbatim copy of the declared plugin directory keyed by its basename).
- Sandbox: `--sandbox` invokes macOS Seatbelt. A prior probe session recorded a throwaway-`HOME` relaunch failure (`getconf DARWIN_USER_CACHE_DIR`) in its managed sandbox; T080 could not reproduce that failure against several fresh throwaway `HOME`s in this session's environment (all live probes below ran with `--sandbox` and a brand-new `HOME` and printed `using macos seatbelt (profile: permissive-open)` successfully) -- treat the earlier finding as environment-specific rather than a permanent 0.22.2 limitation. The adapter still always passes `--sandbox`; no write mode disables it.
- Exit/cancel: provider connection failure still emitted a terminal `result` and exited 0. Agent-run therefore classifies the JSON result, not only the exit code; cancellation uses the existing process-group SIGINT/SIGKILL one-shot session behavior.

## Real-work test (T080)

Scratch repo: `t080-scratch/` (a fresh `git init` inside this worktree, one file `calc.py`, committed). Live child driven the same way as the pings (direct `QwenAdapter.prepare`, `write=True` → `--approval-mode auto-edit --sandbox`), task: add `multiply(a, b)` with a docstring to `calc.py`, add `test_calc.py`, run `python3 -m unittest`, and `git commit` on success.

Result: the child wrote a correct `multiply(a: float, b: float) -> float` with a docstring to `calc.py` and a `test_calc.py` with four passing test cases (verified independently afterward: `python3 -m unittest` → 4/4 `ok`). It then attempted `run_shell_command` for both `python3 -m unittest` and `git add -A && git commit`, and **both were denied** by the sandbox/approval layer -- `auto-edit` auto-approves edit tools (`write_file`) but not `run_shell_command`; only `yolo` (deliberately unused, see Permissions above) would have allowed it. The child noticed the denial, reported it truthfully, and printed the exact commands for a human to run instead of silently giving up. This is the same write/shell asymmetry codex's own read-only-sandbox-vs-network note documents for its runtime -- not a defect in this adapter. **No commit exists from the child itself**; the file edits are real and verified, the commit step is the one item a fully headless `auto-edit` run cannot do on this runtime without `yolo`.
